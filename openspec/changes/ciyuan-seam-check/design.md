## Context

见 proposal.md — Why。所需现状（2026-11-18 实证）：

| 事实 | 证据 |
|---|---|
| 缝点纪律现状 | `paas/docs/sub2api-fork-patches/README.md` §二 = 24 行 Markdown 表格，人读人比 |
| fork 实际改动面 | `git diff --name-status $(git merge-base upstream/main main) main`：156 新增 / 264 修改 / 23 重命名 |
| 改动的上游文件 | 排除 `backend/ent/` 与 `_test.go` 后 **74 个** |
| 上一窗教训 | 2 处缝点外冲突未补登记；5.3 终验未勾即归档（台账 §三 已知挂账） |
| 现有 CI | `.github/workflows/backend-ci.yml`：`shell` + `test`（Go 1.27.3 钉版、unit tests）；另有 `release.yml`、`security-scan.yml` |
| 上游 tag 可查 | `git fetch upstream --tags` + `git tag --list 'v*'`；本地已有 `v0.2.16`–`v0.2.19`，上游已到 0.2.21 |
| openspec CLI 能力 | `openspec validate` / `status` / `archive`；tasks 勾账可解析（`- [ ]` / `- [x]`） |

**约束**：检查不得进入产线二进制；不得要求 fork 侧维护第二份「上游文件清单」；不得让首次落地
因为存量 74 个文件而永久红（必须先做一次性对齐再开闸）。

## Goals / Non-Goals

**Goals**

- 「缝点之外改上游文件」在 CI 上失败，且失败信息能直接指导修复。
- 白名单与人工台账双向可核对。
- 窗口触发与归档前置条件不再靠人记。

**Non-Goals**

- **不做「上游文件内容不被改」的强校验**（即不比对 patch 内容/行级差异）——缝点纪律的本意是
  「改哪里要登记」，不是「改动必须逐字可重放」。行级比对会因上游每次合流都变而永久红。
- 不替代人工台账：白名单是机器侧判据，台账是**为什么**。两者互补，不合并。
- 不在本 change 里做自动开 PR（只做提示），自动开单涉及权限与噪声控制，另行评估。

## Decisions

### D1 判据 = 「上游基线存在的文件」− 「白名单」 ≠ ∅ 即失败

基线取 `git merge-base upstream/<最新已消纳 tag> fork-main`；被改文件取该基线到 HEAD 的 diff。

**关键取舍**：`backend/ent/` 是**生成的**，上游 schema 一变它就跟着变，把它们逐文件登记会让白名单
被生成代码淹没。处理：`ent/` 作为**目录级豁免**，但豁免必须显式写在白名单文件里（`"dir: backend/ent/"`），
不是硬编码在脚本里的魔法路径——这样「谁豁免了什么」一目了然。

**备选**：按 commit 归属判断（哪些提交碰了上游文件）→ 否决（历史已成型，无法回溯；且合并提交会把
上游改动也算进来）。

### D2 白名单格式：JSON，且与台账路径逐条对应

```json
{
  "seams": [
    {"path": "backend/internal/domain/platforms.go", "why": "平台清单（车道注册表）"},
    {"path": "backend/internal/server/routes/gateway.go", "why": "车道路由挂载 + 400 字符断言窗口"},
    {"dir": "backend/ent/", "why": "生成代码，随 schema 变动"}
  ]
}
```

放在**判断逻辑能读到的地方**：仓库内（例如 `backend/scripts/seam-check/allowlist.json`）。
台账 §二 的表格行需含相同路径字符串，检查据此做双向核对（简单包含匹配即可，不解析 Markdown 表格结构）。

**理由**：解析 Markdown 表格很脆；而「台账里出现该路径字符串」已经足以做到「两边都提到了」。

### D3 首次落地必须先做一次性全量对齐

现状 74 个文件没有成文清单。落地顺序：先跑一次检查，把它报出的文件**逐条**与台账比对，补登记，
然后提交白名单与台账的联合变更。开闸后这条检查才是「守住不扩大」而不是「一次性合规」。

**理由**：不这么做的话，第一次开闸必然全红，团队会加个 `--force` 绕过——那就等于没做。

### D4 窗口触发：定时的 tag 比对，不引入 webhook

一个定时任务（CI schedule）比对 `upstream` 最新 tag 与 fork 已消纳基线，落后即产出一条提示
（issue/dashboard 二者择一，按现有仓库习惯）。

**理由**：webhook 要权限配置与公网可达性；定时比对零权限、可测、够用。噪声通过「同 tag 只提示一次」
控制。

**备选**：GitHub Actions `repository_dispatch` 从上游仓触发 → 否决（上游不是我们的仓，无权配置）。

### D5 归档前置：检查 tasks 勾账，不检查「做得对不对」

归档门只做一件事：解析 `tasks.md`，若存在 `- [ ]` 且该项没有「跳过」标记，则拒绝归档。

**理由**：「做得对不对」需要人判断，机器做不了也不该假装能做。而「有没有未勾项」是确定性的。

## Risks / Trade-offs

- [白名单一次性膨胀] 74 个文件全登记 → 白名单变成「现状快照」，失去约束力 → D3 要求逐条带 `why`，且台账必须同步；把「为什么」写下来本身就是约束
- [ent 目录豁免掩盖真实缝点] 目录级豁免可能放过 `ent/schema/*.go`（手写 schema）→ 白名单里把 `ent/schema/` 单独列为缝点，`ent/` 其余子目录豁免
- [定时任务被忽略] 提示没人看 → 与第 6 组收口项联动（窗口延迟进入台账 §三），让「没开窗」在合并时可见
- [误红导致绕过冲动] D3 的一次性对齐 + 失败信息直接给修复指引（「回退或登记」）
- [检查脚本自身腐化] 脚本无测试 → 用少量固定夹具（假 diff 输入）做单测

## Migration Plan

1. 写检查脚本 + 夹具单测（本地可跑）
2. 一次性对齐：跑出 74 个文件 → 与台账比对 → 补登记 → 提交白名单 + 台账联合变更
3. CI 加 job（不阻塞现有 test job 的关键路径：作为独立 job）
4. 定时 tag 比对任务上线，产出一条真实提示验证
5. 归档门前置接入（在归档流程里跑检查，失败拒绝）

**回滚**：删除 CI job 即停用，检查脚本保留无副作用。
