## Why

ADR-0024 的「只增不改、零补丁」纪律目前是**散文**：缝点集合登记在
`paas/docs/sub2api-fork-patches/README.md` §二（24 行表格），靠人记、靠人比。实测代价已经出现两次：

- 上一窗（`merge-upstream-v0-2-19`）有 **2 处缝点外冲突未补登记**，是事后在台账回填时才发现的。
- 上一窗的 `5.3` 终验项**未勾即归档**，归档动作与 tasks 勾账脱节。

当前 fork main 相对上游改了 **74 个非 ent、非测试的上游文件**（+ent、+测试后 264 个文件被修改）。
这个量级下「哪些文件算缝点」用肉眼比对已经不可靠——而缝点集合一旦悄悄变大，"只增不改"就变成了
一句自我安慰。

同时，月度窗的触发器也是散文：上游出了新 tag（本地 VERSION 0.2.18 vs 上游 0.2.21）不会有人自动
知道，上一窗就因此晚了 8 天。

## What Changes

- 新增 `seam-check` 检查：以「相对上游合并基线的 diff 文件集合」减去「缝点白名单」为判据，
  白名单之外的上游文件被修改即失败。白名单以机器可读形式维护（而非只有 Markdown 表格）。
- 白名单本身 MUST 与台账 §二 同源可核对：检查同时校验「白名单 ⊇ fork 实际改动的上游文件」，
  任何人扩大缝点面都必须显式提交白名单变更，从而在评审里可见。
- 新增窗口触发器：上游出现新 tag 或上游 notes 含安全字样时自动开单（把「靠人记得」换成「机器提」）。
- 归档前 tasks 勾账核查：归档动作前必须确认 tasks 全部勾账或有明确跳过理由（上一窗教训）。
- 这些检查作为 CI 任务运行，并可在本地一键执行。

## Capabilities

### New Capabilities

（无——本 change 是把既有纪律做成闸，不引入新的对外行为）

### Modified Capabilities

- `ciyuan-upstream-sync`: 新增「缝点集合不得在无人察觉的情况下扩大」与「窗口触发与归档前置条件
  机械化」两条要求——把 §二 白名单与 tasks 勾账从人工纪律升级为可失败的检查

## Impact

- **代码/工具**：新增检查脚本 + CI job（不进入产线二进制，不影响运行时）
- **数据**：零 schema、零迁移
- **流程**：扩大缝点面从「改一个上游文件顺手」变成「必须同时改白名单」——这是本 change 的**主要
  收益也是主要代价**（多一点仪式感，换掉无声漂移）
- **风险**：白名单若一开始就不全（现状 74 个文件没有成文清单），首次落地会「全红」→ 必须先做一次
  一次性对齐（把现有改动全部登记），再开闸
